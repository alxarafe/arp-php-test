# ARP PHP integration test application

PHP 8.5 + MariaDB 12.3 + PDO, with no application framework or ORM. This is an
**application consuming ARP**, not an implementation of `arp-php`. The initial
infrastructure is independent of ARP while its library API is being defined.

## Run locally

```bash
cd ~/Desarrollo/Alxarafe/arp-php-test
cp .env.example .env
docker compose up --build -d
curl http://localhost:8088/health
docker compose exec app php bin/console modules:list
docker compose exec app php bin/console modules:install catalog
docker compose exec app php bin/console modules:enable catalog
docker compose exec app php bin/console modules:diagnose
./bin/check
```

To deactivate without dropping tables:
`docker compose exec app php bin/console modules:disable catalog`.

The starter does not yet depend on an unpublished `arp-php` package. Once the
library provides a public Composer interface, add a local Composer path repository
pointing at `../arp-php`, pin its version, and register its services from module
bootstraps. Do not copy ARP internals into this application.

## Module lifecycle (PHP-TEST-MOD-001 MVP)

Each direct child folder of `modules/` containing a valid `module.yaml` is a
candidate. Discovery alone does **not** execute code or SQL. The folder name and
module ID must match. `bootstrap.php` is executed only for installed + enabled
modules on application boot. An installed but disabled module retains its data.

`modules:install` runs trusted `database/install/*.sql` files lexically, **one
statement per file**. These scripts must be idempotent; MariaDB DDL is generally
not transactional. If installation fails after a DDL change, retry only after
inspecting state. No automatic uninstall, migrations, marketplace or hot reload.

Dependencies are installed and enabled explicitly. Missing dependencies, active
cycles and duplicate IDs are errors. Disabling a module with enabled dependents
is blocked. The application is restarted after module state changes to refresh
processes other than short-lived CLI and PHP built-in server requests.

Modules are trusted executable PHP code; do not install untrusted plugin folders.
The SQL constraints are intentionally application-owned, not generated by ARP.

## Tests

`composer test` runs unit tests. `composer test:integration` uses **only** the
dedicated `arp_php_test_integration` database created on fresh MariaDB startup.
Integration tests are destructive to that test database and should not run
concurrently. `./bin/check` invokes both suites in the container.

This infrastructure does **not** yet claim ARP-DICT-001 conformance. The sample
catalog and reference tables provide a future integration fixture for the SKU.

## Environment

`APP_PORT` defaults to 8088 and is bound to loopback. Do not expose the demo HTTP
server publicly. MariaDB is internal to Docker Compose; `.env` must never be
committed. Change development-only passwords before use outside local testing.

## Docker extensions and validation

The official `php:8.5-cli-bookworm` image already includes DOM, Lexbor, mbstring,
SimpleXML, XML and XMLWriter. The Dockerfile builds only `pdo_mysql` and `zip`,
installs `unzip`, and checks all required PHP extensions during the build.
Rebuilding DOM separately is unnecessary and can fail to find the bundled
Lexbor headers (`lexbor/html/parser.h`).

Composer installs the versions in `composer.lock` at application startup and
generates `vendor/autoload.php` before initializing the module registry.

Validated with PHP 8.5.12 and MariaDB 12.3.3: Docker build and startup, Composer
installation and platform requirements, HTTP `/health`, catalog discovery,
installation, enable/disable, diagnosis, and enabled-state persistence after
restarting both services. `bin/check` passed 4 unit tests (5 assertions) and
1 integration test (7 assertions). Run it again after subsequent changes.
